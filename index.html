You're Shipping AI Output Without a Second Opinion. Here's How to Fix That.

Most AI pipelines look like this: send prompt, get output, ship it. Maybe you skim it. Maybe you don't. The model sounds confident, the output looks reasonable, and you move on.

The problem is not that the output is always wrong. It is that you have no systematic way to catch when it is. One model, one pass, no pushback. Confident errors look identical to confident correct answers.

The fix: add a second model whose only job is to challenge the first one. Not summarize it. Not reformat it. Challenge it — and force a revision loop until it approves or you escalate to a human.

This post covers the pattern, where it applies, and a full worked example to make it concrete.

TL;DR

Two models, one task. Agent A proposes output. Agent B audits it with structured feedback and a machine-parseable verdict. They iterate until approved or a round cap triggers human review. Every decision is logged.

The worked example is a Claude Code slash command for grading Jupyter notebooks (full skill on GitHub) — Claude grades, Codex audits in read-only mode, up to 5 rounds, final scores write to CSV. But the pattern generalizes to any pipeline where you are currently shipping single-model output without a verification layer.

The Pattern: Two-Model Adversarial Review


                Round 1:
                  Agent A reads context + task
                  → produces draft output
                  → sends to Agent B for audit

                Round 2..N:
                  Agent B returns VERDICT: REVISE + structured issues
                  → Agent A updates draft, carries full state
                  → Agent B re-checks in same session context

                Stop:
                  VERDICT: APPROVED → ship output + log
                  round == max → flag for human review + log

Three things make this work in practice:

Strict verdict protocol. Agent B must return a machine-parseable signal — VERDICT: APPROVED or VERDICT: REVISE — not free-form prose. Automation needs a deterministic stop condition. Prose is not one.

Structured issue format. Vague critique ("this looks off") does not give Agent A enough to act on. Structured feedback (ISSUE: <location> | PROBLEM: <description> | SUGGESTED_FIX: <value>) does. It also makes it easy to detect no-op loops — if Agent A already applied all suggested fixes, treat the round as approved.

Explicit state on resume. Agent B needs to see what changed between rounds, not just the current output. Without a state delta, it will repeat prior feedback even after issues are resolved. Carry the full current draft plus a per-issue change summary on every resume prompt.

One model gives you an answer. Two models give you a verified answer.

Where This Pattern Applies

Any pipeline where you are currently taking single-model output at face value is a candidate.

Code review. Agent A writes or refactors code. Agent B audits for correctness, edge cases, and logic errors. Particularly valuable for catching subtle bugs that look right syntactically but break on real inputs.

Document QA. Agent A drafts a contract, report, or policy doc. Agent B checks for internal inconsistencies, missing clauses, or factual gaps. Single-model output consistently misses contradictions it introduced itself.

Content moderation. Agent A classifies content. Agent B audits borderline cases and flags disagreements for human review. Reduces both false positives and overconfident calls on ambiguous inputs.

Test generation. Agent A writes unit tests. Agent B checks whether they actually cover the specified behavior and would catch the bugs they claim to. Single-model test generation often produces tests that pass trivially without testing anything meaningful.

Rubric-based grading. Agent A scores student submissions. Agent B audits for evidence mapping, rubric alignment, and over-credit on output that looks right but is subtly wrong. This is the worked example below.

The pattern applies whenever: output quality is hard to verify by inspection alone, errors are subtle rather than obvious, and consistency across a batch matters.

Worked Example: Grading Notebooks with Claude + Codex

I built this as a TA grading Quiz 2 notebooks. Claude handles grading and revision. Codex audits in read-only mode. A Python orchestration script manages state, loop control, and writes final artifacts.

Grading is a good test case because it has all the properties that make single-pass output dangerous: rubric criteria are subtle, over-credit on plausible-but-wrong answers is easy, and you are processing 40+ submissions where consistency drift is a real problem.

Implementation


                Round 1:
                  Claude reads rubric + extracted notebook text
                  → writes draft JSON scores and rationales
                  → run_grading_loop.py sends prompt to Codex
                  → Codex responds VERDICT: APPROVED or VERDICT: REVISE

                Round 2..N:
                  Claude updates draft from ISSUE lines
                  → run_grading_loop.py resumes same Codex session
                  → Codex verifies whether those fixes were actually applied

                Stop:
                  APPROVED → append to grades CSV + log final section
                  round == 5 → append anyway and flag for human review

Codex runs read-only — it flags issues, it does not change output directly. Session resume uses an explicit session ID so Codex remembers what it flagged and can verify whether the latest draft actually addressed those exact points, not just acknowledged them.

What it caught

In one concrete case, Codex flagged over-credit on a notebook where predicted hazard used the wrong fitted-variable reference during parameter extraction. The code looked right. The variable was wrong. That is exactly the kind of subtle error that passes a single-pass review every time.

Single-pass vs. two-model: the comparison

❌ Manual ⚠️ Single-pass ✅ Two-model
Speed Slow Fast Fast-ish
Consistency Drifts High High
Catches subtle errors Sometimes Rarely Yes
Pushback on bad output None None Structured, per-issue
Audit trail None None Full
Human escalation Always Never On cap-hit

Bugs Worth Knowing About

No state delta on resume. Agent B repeated prior feedback even after output changed, because the resume message said "updated" without showing what. Fix: carry the full current draft plus a per-issue change summary in every resume prompt. Resume is not a magic diff.

No-op REVISE loops. Agent B re-issued a suggested fix that was already applied. Fix: before sending a resume prompt, check whether all suggested values already match the current draft. If they do, treat the round as approved.

How to Adapt This

  1. Define the task boundary — what Agent A produces, what Agent B is allowed to do.
  2. Lock in a strict verdict format before writing any orchestration logic.
  3. Design the issue format so fixes are unambiguous and checkable.
  4. Build and validate the single-round path before adding resume logic.
  5. Set a round cap and a human escalation path before running on real data.

The infrastructure is minimal: two model calls per round, a session ID, a log file, and a state-carrying resume prompt. No queues, no databases, no distributed anything.

The Core Tradeoff

Two-model review adds setup cost and slightly more time per output. For one-off tasks or highly subjective output, it is probably not worth it. For high-volume, high-stakes, or consistency-sensitive pipelines — grading, code review, compliance checking, moderation — the audit trail and adversarial pressure pay off quickly.

The goal is not to remove humans from the loop. It is to make sure that when something reaches a human, it has already been challenged once.
